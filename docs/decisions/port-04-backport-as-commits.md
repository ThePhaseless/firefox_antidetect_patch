# port-04: a backport is a list of commits, replayed on the tag

**Rule.** A backport of third-party code is carried as the ordered list of upstream commits it needs plus our own commits, all stored in the series: the folder's `BACKPORT.json` lists them (`file`, `sha256`, `kind` upstream, ours or test, `upstream_sha` for a pick, `contained_in`), and `commits/` holds one patch file per commit. `engine.py` replays them onto the exact revision the tag vendors, drops those the revision already contains (a commit is contained only when its patch applies in reverse with its full context; a patch that fits neither forward nor in reverse is a conflict for a human, never a guess), and regenerates the `.cargo-checksum.json` files with a tool (`tools/regen_checksums.py`), never merged by hand. A commit that leaves when upstream merges it is recorded with the upstream revision that contains it (`contained_in`). The Cargo.toml table of an added dependency and the Cargo.lock line that goes with it are produced by rule from the commit (the workspace table it expands is `workspace_dependencies` in `BACKPORT.json`); a step the tool cannot produce stops the replay, and is never carried as text.

**Enforced by.** `check`: the record and its commit files are checked offline (every file present with the recorded sha256, no file unlisted, no reference to a path outside the series, no clone named as the home of our commits); with `--against <tag>` the vendored part of the folder's `hooks.patch` (the crates under `third_party/rust/` and `Cargo.lock`) and the files it adds to `src/` must equal the replay of the commit list on the revision the tag vendors, checksum lines included. A checksum line the tool did not produce fails. The hooks of the folder in Mozilla's own files are not part of the replay and stay under the hook rules.

**Why.** At the port to firefox-160, 7 of the 13 conflicts came from one hand-merged patch (five checksum lines and two code hunks). Replaying the commits gives the two code conflicts alone, and drops by itself the four picks that Mozilla vendored since unchanged; a fifth, which Mozilla has too but with the lines next to it changed, is a third conflict, for a human. The twelve fixes of ours lived only in a branch of one PC; a patch file in the series is the only place they can be reviewed, replayed and kept when the PC is gone.

**Files.** `tools/backport_replay.py` (the replay, `check`, `expect`, `record`, `apply`), `tools/regen_checksums.py`, `tools/engine.py` (`backport_record_problems`, `backport_replay_problems`, `port`), `tools/tests/test_backport_replay.py`, `<folder>/BACKPORT.json`, `<folder>/commits/`; [backport-01](backport-01-upstream-code-as-is.md), [UPDATE.md](../UPDATE.md).

**Don't.**
- Edit a commit file, `hooks.patch`, a `.cargo-checksum.json` line or an upstream file in `src/` of a replayed folder by hand: change the list of commits, then let the replay and `export` write them.
- Copy upstream code into `src/` or into our own commit when an upstream commit has it: pick the commit, so the day Mozilla vendors it the replay drops it.
- Name a clone, a branch of a clone or any path outside the series as the home of a commit.
- Resolve a conflict of the replay in `hooks.patch`: rebase the commit that conflicts onto the revision Mozilla vendors and store its new patch file with its new sha256.
