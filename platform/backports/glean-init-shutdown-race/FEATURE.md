# platform/backports/glean-init-shutdown-race

Category: backport
Prefs: none read directly
Test: `dispatcher::test::flush_init_runs_final_task_after_full_preinit_buffer` of glean-core (src/dispatcher/mod.rs, carried by commit 0002), run by the cargo-tests suite (a third standalone run in third_party/rust/glean-core, floor 1 in scripts/ci/cargo_oracles.py): on the crate as vendored, without the backport, the filter matches no test and the verdict is red; with it the test runs and is green

## What it does

Mozilla bug 2072668, mozilla/glean pull request 3727 (merged 2026-10-30, tip 2874dc1ef164a09f1424a7c4578ec92a1eec4fe0): a race between
Glean's init thread and `shutdown()`. The init thread flushed the pre-init queue and then, on its own thread, recorded
`glean.error.preinit_tasks_overflow` and the `pre_init` health ping (`record_dir_info_and_submit_health_ping`) through the synchronous
API. A process that shuts down right after it starts (a gtest does) lets `shutdown()` close the rkv database in between, and the
synchronous call panics in `storage()` ("No database found"); the panic aborts the process.

The three commits of the pull request change `flush_init` to take a final task, which the dispatcher runs after the pre-init tasks and
before any later one, even when the pre-init buffer is full. The overflow metric and the health ping are recorded there, and
`shutdown()` waits for the dispatcher before it closes the database.

Not ours: the folder has no budget. BACKPORT.json lists the three commits (`commits/`, the sha256 of each, the upstream sha), narrowed to
`glean-core/src/` (the changelog and the benchmarks of the pull request are not vendored), and `backport_replay.py` replays them on
glean-core 70.2.1, the release Mozilla vendors in Firefox 159 (`vendored_crate`; upstream's tag v70.2.1 is revision 1208715a85f7, the one
in the crate's `.cargo_vcs_info.json`). No adaptation was needed: the three commits apply to 70.2.1 as they are. `hooks.patch` (its
vendored part, checksum line included) is what the replay produces, and `check --against <tag>` fails when it is not.

The folder goes when Mozilla vendors a glean-core that has commit 2874dc1ef164: at that port the replay finds the commits already in the
revision and the folder is taken out. Which Firefox release that is, is not known: Bugzilla 2072668 (a tracking bug for the crash signature) was still NEW on 2026-11-25, with Firefox 159 wontfix, 160 affected and 161 to 163 unset.

## Hooks in Mozilla files

- `third_party/rust/glean-core/.cargo-checksum.json` (the hashes of the files the backport changes, hard): regenerated by the tool.
- `third_party/rust/glean-core/src/dispatcher/global.rs` (flush_init, hard): upstream code, `flush_init` takes the final task.
- `third_party/rust/glean-core/src/dispatcher/mod.rs` (DispatchGuard::flush_init and the test module, hard): upstream code, the final task is queued behind the pre-init tasks; the unit test of the pull request.
- `third_party/rust/glean-core/src/lib.rs` (initialize_inner after the pre-init flush, hard): upstream code, the overflow metric and the health ping are recorded in the final task.
